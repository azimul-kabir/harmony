# Harmony v3.0.0 Preview Notes

**Status:** development preview; not a stable release

**Upgrade path:** v2.1.0 → v3.0.0

Harmony v3 focuses the application on its core acquisition and synchronization
workflow:

**Sources → Downloads → Library → M3U/Navidrome**

The preview uses the existing database and migration chain. Do not delete or
recreate `harmony.db` when testing it. Back up the database, `.env`, playlist
files, and artwork cache before switching an existing installation to a preview
image.

## Core workflow retained

- Authenticated, mobile-first web and PWA interface.
- Spotify and public YouTube Music playlist Sources.
- Exact recording acquisition followed by controlled, identity-validated
  fallback matching.
- Explicit user-approved YouTube fallback for unresolved downloads.
- Persisted retries, provider cooldowns, cancellation, and worker recovery.
- Library indexing, duplicate detection, M3U export, and Navidrome scan
  controls.

## Product surface removed or reduced

- Synology host monitoring and provider diagnostics console.
- Metadata discovery, ranked suggestions, application/rollback workflows, and
  persisted metadata-health rules.
- Smart Collections, generated auto-playlists, lyrics UI, and detailed Library
  analytics.
- Navidrome Love/Unlove, direct playlist mutation, playback-stat ingestion, and
  automatic catalog reconciliation.

Historical migrations, tables, and columns can remain for safe upgrades. Their
presence does not mean the removed feature is still active. Runtime and UI code
will be pruned incrementally after import, route, scheduler, and upgrade checks
prove each deletion safe.

## Recent reliability fixes

- A provider no-match result is recorded as **skipped**, rather than failed,
  when Harmony can identify an available copy of the requested recording in
  the Library. The source identity is linked to that existing song, so playlist
  availability remains correct.
- The Downloads details drawer is no longer re-created for every SSE snapshot.
  Users can scroll to and operate the manual fallback form without the panel
  jumping to the top; genuine state changes refresh in place while retaining
  the scroll position.
- The dashboard Downloads and Library Health summaries now occupy two equal
  columns instead of leaving a blank third slot.

These changes apply to new outcomes. Existing rows already stored as failed are
not rewritten automatically.

## Container publication

Pull requests run both the Python CI job and a production Docker build, but the
image is not pushed. Registry publication occurs only on these events:

| Event | Published tag |
| --- | --- |
| Push to `codex/harmony-v3-completed` | `v3-preview` and `sha-*` |
| Push to `main` | `latest` and `sha-*` |
| Push of a `v*` Git tag | the Git tag and `sha-*` |
| Manual workflow dispatch | metadata-generated tags, when applicable |

Published images currently use `linux/amd64`, matching Intel-based Synology
models such as the DS220+.

```bash
docker pull ghcr.io/azimul-kabir/harmony:v3-preview
```

## Preview validation checklist

1. Back up the persistent database and configuration.
2. Pull the preview image and retain the existing volume mappings.
3. Confirm `/health/ready`, login, Sources, Downloads, Library, and Playlists.
4. Test an exact download, an already-owned skip, and one manual fallback.
5. Confirm generated M3U files and request a Navidrome scan.
6. Keep the previous stable image reference available for rollback. Database
   rollback across migrations is not implied by switching the image tag.

See the [roadmap](../roadmap.md) for the remaining cleanup sequence and release
gates. Stable v2.1.0 deployments should continue using the v2.1.0 release until
the v3 release gates are complete.
